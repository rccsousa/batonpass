# S5 — Universal Clipboard × BatonPass loop safety

**Status: resolved. A reliable mechanism exists for the inbound (read) half.
The outbound (write) half has a mitigation that is good but not provably
sufficient, so it must not be the only defence.**

Run on `relay-mac`, macOS 26.3 (build 25D125), Apple Swift 6.2.3, against
`iphone-example` on the same Apple Account, Bluetooth on, Wi-Fi radio on.
Universal Clipboard was live throughout and was exercised in both directions
with the user physically operating the iPhone.

Everything in §1–§3 is **observed on this hardware**. Inferences are labelled.
Raw transcript: `observations.txt`. Probe source: `pbprobe.swift`.

---

## 0. Answers, up front

| Question | Answer |
|---|---|
| Can a UC-delivered item be reliably distinguished from a local copy? | **Yes.** UC-delivered items carry the type `com.apple.is-remote-clipboard`. Local copies never did. |
| If the iPhone sends directly *and* UC delivers to the Mac, does Windows get it twice? | **Yes, unless the Mac agent filters on that marker.** The envelope-level replay dedup in PLAN §3.4 does **not** catch it. |
| Can a BatonPass-written item on the Mac echo back out? | **Not into a loop.** UC does re-export the Mac agent's write to the iPhone, but the iPhone only transmits on an explicit Back Tap, so there is no automatic cycle. `prepareForNewContents(.currentHostOnly)` suppressed the re-export in 4 of 5 trials — see §3. |
| Does the plan's loop suppression (content hash + `changeCount`) survive UC? | **Yes, and it stays necessary.** UC does not break it; UC adds a *second* problem (inbound duplication) the hash would mask rather than solve. |

The acceptance criterion in `TASKS.md` is met by the first branch: there **is** a
reliable mechanism to ignore UC-originated items. The Mac agent does **not** need
to be off while the iPhone sends directly.

## 1. OBSERVED — the inbound (read) case is cleanly distinguishable

Every row is a real `changeCount` transition captured live by `pbprobe`.
Types are in the order `NSPasteboardItem.types` returned them.

| # | cc | Origin | `NSPasteboardItem.types`, in order |
|---|----|--------|------------------------------------|
| 1 | 286 | `printf 'local-test-pbcopy-A' \| pbcopy` | `public.utf8-plain-text` |
| 2 | 287 | `pbcopy` again | `public.utf8-plain-text` |
| 3 | 288 | agent write (`clearContents` + `setString`) | `public.utf8-plain-text` |
| 4 | 289 | agent write + self-stamp | `public.utf8-plain-text`, `org.nspasteboard.source` |
| 5 | 290 | `pbcopy` | `public.utf8-plain-text` |
| 6 | **291** | **iPhone copy → UC** | `public.utf8-plain-text`, `public.text`, **`com.apple.is-remote-clipboard`** |
| 7 | **292** | **iPhone copy → UC** (2nd tap) | same three |
| 8 | **293** | **iPhone copy → UC** (single tap) | same three |
| 9 | 294 | GUI Cmd-C in Obsidian | `public.html`, `public.utf8-plain-text`, `org.chromium.internal.source-rfh-token`, `org.chromium.web-custom-data`, `org.chromium.source-url` |

**The discriminator is the presence of the type `com.apple.is-remote-clipboard`.**
It appeared on all three UC deliveries and on none of the six local or
agent-written items, including the rich-typed GUI copy.

Properties of the marker, all observed:

- It is a **type**, not a value. `data(forType:)` returns a **zero-byte `Data`**,
  `string(forType:)` returns `""`, `propertyList(forType:)` returns `nil`.
  Detection must be `item.types.contains(...)` — a truthiness test on the value
  evaluates false and silently fails open.
- It appears in **both** `NSPasteboard.types` (the union) and the per-item
  `NSPasteboardItem.types` array.
- It is visible **without reading any data**. The probe inspects in two phases
  (types-only, then data) and `changeCount` did not move between them: the agent
  can classify an item before materialising its payload.
- For short text, UC delivers **eagerly and fully materialised** — the Mac's
  `changeCount` bumped within a second of the iPhone copy with no paste on the
  Mac, and the 13–14 byte payload was already readable. No promise to pull.
- **One copy = one delivery = `changeCount` +1.** The double delivery at cc
  291/292 was the user tapping Copy twice, confirmed with him directly. UC did
  not spontaneously re-deliver.

### 1.1 What is *not* there

Explicitly probed on every change and **never present** on any item:
`org.nspasteboard.TransientType`, `org.nspasteboard.ConcealedType`,
`org.nspasteboard.AutoGeneratedType`, `org.nspasteboard.IgnoreType`,
`org.nspasteboard.source`, `com.apple.pasteboard.promised-*`.

The `org.nspasteboard.*` conventions are a third-party community agreement
(nspasteboard.org) honoured by some clipboard managers. macOS knows the strings —
they are present in the dyld shared cache — but **Universal Clipboard does not
stamp any of them**. Useless as a UC discriminator. They are usable by BatonPass
for its *own* writes: row 4 shows a self-stamped `org.nspasteboard.source` is
accepted, persists, and reads back intact.

### 1.2 NSPasteboard exposes no provenance API at all

Checked against the macOS SDK headers, not from memory. `NSPasteboard` has no
source, owner, origin, or device property. The only `owner` concept
(`declareTypes:owner:`, `NSPasteboardTypeOwner`) is the lazy-promise callback
object and says nothing about where an item came from. `accessBehavior`
(macOS 15.4+, observed value `2`) is this app's *pasteboard permission state*,
not provenance.

`com.apple.is-remote-clipboard` is the only signal that exists.

### 1.3 The cost: the marker is undocumented

A full search of the macOS SDK (`$(xcrun --show-sdk-path)`) found **zero**
occurrences of `is-remote-clipboard`. The string is present in the dyld shared
cache, so it is a real system constant, but it is **not public API**. Apple can
change or remove it in any release without notice.

*Inference, not observation:* it is a long-standing convention (clipboard
managers have used it to suppress Handoff items for years) and is unlikely to
vanish quietly — but that is a bet, not a guarantee. Mitigation in §4.3.

### 1.4 One unexplained observation — non-text items

The probe's first snapshot (cc 285, before any test) showed a pre-existing item
with types `com.apple.uikit.image`, `public.heic`, `public.png`, `public.jpeg` —
a `com.apple.uikit.*` type implies iOS origin — carrying **no**
`com.apple.is-remote-clipboard` marker.

I could not attribute how that item reached the Mac (UC, iPhone Mirroring,
Continuity Camera, AirDrop and Messages are all candidates) and did not test
image transfer, so **this is not evidence that the marker fails for images** —
it is an unresolved loose end. It does not affect Phase 1, which is text-only by
design (`PLAN.md` §3.9). If image support is ever added, re-run this spike for
image types first.

## 2. OBSERVED — the duplicate-delivery question

```
iPhone copy
   ├── Back Tap → BatonPass → relay → Windows        (intended)
   └── Universal Clipboard → Mac                     (automatic, unavoidable)
             └── Mac agent sees changeCount +1 → relay → Windows   (duplicate)
```

**Without a marker check, Windows gets it twice.** Established by construction
from §1: the Mac's pasteboard genuinely changes, with the real payload, within a
second of the iPhone copy and with no user action on the Mac.

**The replay defence in `PLAN.md` §3.4 does not prevent this.** That dedup key is
`(epoch, sender-ID, event-ID)`. The Mac's re-send is a *different sender* with a
*different event ID* carrying the *same content*. It is a legitimately new event
by every envelope-level test. Only content-level or provenance-level filtering
catches it, and provenance is the correct one — content-level dedup would also
swallow a deliberate re-copy of the same text.

**Fix:** the Mac agent must not send any item whose `NSPasteboardItem.types`
contains `com.apple.is-remote-clipboard`. One guard, at the top of the change
handler, before anything else.

## 3. OBSERVED — the outbound (write / echo) case

### 3.1 There is no automatic loop

*Structural, and it is the load-bearing fact here.* A UC re-export of the Mac
agent's write lands on the **iPhone's pasteboard**, and the iOS leg of BatonPass
transmits **only on an explicit Back Tap** (`PLAN.md` §1.2 — iOS cannot read the
pasteboard in the background, by OS design). No code path turns an item arriving
on the iPhone into a send. **A runaway echo loop is not reachable**, independently
of any flag.

The residual risk is bounded and mild: the user's iPhone clipboard gets
overwritten by whatever the Mac agent received from Windows — arguably the
desired behaviour of a clipboard-sync tool.

### 3.2 `.currentHostOnly` — what the tests actually showed

`NSPasteboardContentsCurrentHostOnly` is **public API** (AppKit, macOS 10.12+),
documented in the SDK header as "the pasteboard contents should not be available
to other devices":

```swift
pb.prepareForNewContents(with: [.currentHostOnly])   // rawValue 1, verified
pb.setString(text, forType: .string)
```

Five write trials, each verified on the iPhone by the user pasting into Notes:

| Payload | Written with | Reached iPhone? |
|---|---|---|
| `NORMAL-ZETA` | plain `clearContents` + `setString` | **YES** (control — proves the export path was live) |
| `LOCALONLY-GAMMA` | `.currentHostOnly` | **YES — leaked** |
| `HOSTONLY-EPSILON` | `.currentHostOnly` | no |
| `HOSTONLY-THETA` | `.currentHostOnly` | no |
| `HOSTONLY-KAPPA` | `.currentHostOnly`, 0.4 s after an exportable `pbcopy` | no |
| `HOSTONLY-MU` | `.currentHostOnly`, then a 2.5-minute wait | no |

The flag held 4 times out of 5 and leaked once.

I tried to reproduce the leak. Hypothesis: UC advertises on an exportable change
and the iPhone fetches from the *live* pasteboard later, so a host-only write
landing inside that window would be served instead. `HOSTONLY-KAPPA` was built to
trigger exactly that and **did not reproduce it** — instead *neither* item
crossed, meaning the host-only write appears to have cancelled the pending
advertisement for the preceding legitimate copy. `HOSTONLY-MU` then ruled out
"the flag only delays export".

**The leak is unexplained and I could not reproduce it.**

### 3.3 Why the four negatives are weaker evidence than the one positive

Mac → iPhone delivery is verified only by the user pasting, which is a
pull-triggered path with real latency. It was demonstrably **flaky** during
testing: `BAIT-IOTA`, an ordinary `pbcopy` with no flag at all, never arrived on
the iPhone either. So "did not arrive" is consistent with both "the flag blocked
it" and "UC was simply asleep". "Did arrive" is unambiguous.

The single `LOCALONLY-GAMMA` leak is therefore **strong** evidence that
`.currentHostOnly` is not an absolute guarantee. The four blocks are
**suggestive** evidence that it usually works.

**Design consequence: use the flag, but never rely on it alone.** The
receive-side suppression must be correct on its own.

### 3.4 The plan's existing loop suppression survives UC

`PLAN.md` §3.9 specifies last-written-content-hash plus `changeCount`. Against
what was observed:

- UC deliveries produce ordinary `changeCount` +1 transitions — the counter
  behaves normally, so `changeCount`-based change detection is unaffected.
- An agent write produces exactly one `changeCount` +1 (observed at cc 288, 289,
  295, 298, 299, 300, 302, 303). No phantom bump, so the agent reliably
  recognises its own write.
- A UC re-export of the agent's own write goes to the **iPhone**, not back to the
  Mac's pasteboard. It never re-enters the Mac's change stream, so it cannot
  defeat the hash.

UC adds no new echo path on the Mac. It adds the **inbound duplication** problem
of §2, which the content hash would paper over by coincidentally matching, rather
than solve — and which would fail the moment the two paths differ by so much as a
trailing newline. The marker check in §2 is the real fix; the hash stays for what
it was already for.

## 4. Required changes to T8 (macOS agent)

### 4.1 Drop UC-delivered items — mandatory

In the `changeCount` change handler, before hashing, before sending:

```swift
let uc = NSPasteboard.PasteboardType("com.apple.is-remote-clipboard")
guard let item = pb.pasteboardItems?.first else { return }
if item.types.contains(uc) { return }   // Universal Clipboard delivered this; the iPhone owns it
```

Test `types.contains`, **not** the value — the value is a zero-byte `Data`.
Check before reading payload data; the marker is visible in the type list alone.

### 4.2 Write with `.currentHostOnly` — belt, not braces

```swift
pb.prepareForNewContents(with: [.currentHostOnly])
pb.setString(text, forType: .string)
```

Keeps the agent's writes off the iPhone in the normal case. Per §3.3 it is a
nicety, not a safety mechanism — §4.1 plus the existing content hash are what
make the system correct. The SDK header's sticky-option semantics ("options
persist until `prepareForNewContentsWithOptions:` or `clearContents`") mean the
flag must be passed on **every** write, never assumed to carry over.

### 4.3 Make marker loss loud, not silent

The marker is undocumented (§1.3). If a macOS update removes it, §4.1 fails
**open** — the Mac silently starts duplicating every iPhone copy to Windows.

Add a self-check: if the agent has never observed an item carrying
`com.apple.is-remote-clipboard` over its lifetime while UC-capable peers exist,
surface that in the agent's status output. Not a crash — but it converts a silent
correctness failure into a visible one.

*Inference:* this is the same fail-closed posture the plan already applies to
replay state (§3.4), extended to an undocumented dependency.

### 4.4 No change needed to iOS, Windows or the relay

The fix is entirely local to the macOS agent.

## 5. Reproducing this

```
swiftc -O -o pbprobe pbprobe.swift

./pbprobe                          # watch; dumps every changeCount change
./pbprobe once                     # one snapshot
./pbprobe write TEXT               # case 3: naive agent write
./pbprobe write-marked TEXT        # agent write with an org.nspasteboard.source self-stamp
./pbprobe write-localonly TEXT     # agent write with .currentHostOnly
```

For the UC case there is no substitute for a second Apple device: copy on the
iPhone with both devices on the same Apple Account, Bluetooth and Wi-Fi on, and
watch the Mac. It cannot be simulated.
